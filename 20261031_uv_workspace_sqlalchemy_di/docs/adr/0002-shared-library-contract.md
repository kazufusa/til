# ADR 0002: 基盤ライブラリの契約

## ステータス

採用(2026-11-01)。[ADR 0001](0001-shop-core-owned-shared-library.md) を置き換えます。

## コンテキスト

ADR 0001 で、共有パーツを基盤チームが所有するライブラリとして配ると決めました。
その後、次の事情が加わりました。

- プロセスの種類が増えました。同期の Web、async の Web、async のエージェント、ジョブです
- 接続情報が 1 本の URL ではなく、環境ごとに別の経路から来ます。秘密情報はローテーションされます
- DB のロールが、アプリ用とマイグレーション用に分かれます
- 成果物を DB の外(オブジェクトストレージ)に置きます
- 同じ集約を複数の経路が同時に更新します
- チームをまたいで例外の分類を揃える必要があります
- commit の後に外へ知らせを出す必要があります
- DB なしのテストで、一意制約や版の衝突まで再現したい要望があります

ADR 0001 の決定のうち変えないものは、ここに再掲します。
この文書だけ読めば契約が分かる状態にします。

## 検討した選択肢

- 組み立てを import 時に走る初期化関数で行う: 不採用。import 順で挙動が変わり、戻り値が無いので差し替えもできないため
- 組み立てを戻り値のある関数にし、入口で 1 回呼ぶ: 採用
- DB 層を同期と async の 2 本持つ: 不採用。リポジトリが二重になり、プールも 2 つになるため
- DB 層は同期 1 本で、async からはスレッドで呼ぶ: 採用
- 同時更新を行ロックだけで守る: 不採用。読んで考えて書く間の衝突を検出できないため
- 集約ごとに行ロックと版の楽観ロックを使い分ける: 採用
- 不変条件をサービスだけで守る: 不採用。直接書き込みを許す以上、DB 制約が要るため
- DB 制約を宣言して、本物の翻訳とフェイクの検査を同じ定義から引く: 採用
- 保存先のキーの規則をドメインに置く: 不採用。保存の仕方は infra の責務で、ドメインに保存の語彙が入るため
- キーの規則をアダプタに置き、ポートはエンティティを受け取る: 採用
- commit 後の知らせに Outbox を使う: 不採用。この規模では運用の負担が見合わないため。送り側が 1 回以下になる点は受け入れる
- 例外を自由に増やす: 不採用。境界での変換が増え続けるため。code と 3 分類に揃える

## 決定

### 公開面と所有

基盤チームがライブラリを所有し、uv workspace のメンバーとして配ります。
アプリが import してよいのは、`__all__` にある名前、`shop_core.tables`、`shop_core.testing` だけです。
`infra` と `usecase` の内部は予告なく変えます。
サービスやテーブルを足す PR は、それを要るチームが書きます。
基盤チームは CODEOWNERS で必須レビュアーになり、レビューして取り込みます。
「基盤の手を通る」とは、基盤が書くことではなく、基盤がレビューすることです。

### 組み立て

import 時には何も実行しません。定義だけです。
組み立ては `build_container(settings)` が行い、`Container` を返します。
戻り値が唯一の持ち手で、モジュール変数には置きません。
呼ぶのはプロセスの入口 1 箇所です。FastAPI の lifespan か `main()` です。
検査は 2 段です。`validate_environment` は I/O なしで設定の形を見ます。
`check_database` と `check_image_store` は接続して確かめ、使うプロセスだけが呼びます。
Engine は `container.engine()` を最初に呼んだときに作られます。
`build_container` 自体は接続しません。

### 接続と資格情報

Engine の作り方は `Container(engine_factory=...)` で外から差し込めます。
渡さなければ `Settings.from_env()` から作ります。
資格情報がローテーションされる環境では、`build_container(credentials=fn)` を使います。
新しい接続を張るたびに `fn` を呼び、認証失敗のときだけ取り直して 1 回やり直します。
起動時に読んで固定することはしません。
DB のロールは 2 つです。アプリ用は USAGE と DML だけ、マイグレーション用は DDL を持ちます。
ロールの作成は DB の初期化で行い、GRANT はマイグレーションで行います。
`assert_app_role` が起動時に、アプリが DDL を持つロールで入っていないことを確かめます。
スキーマ名は `infra/schema.py` の定数 1 つで、`public` は使いません。
環境変数の名前と既定値は基盤の規約で、一覧は README に置きます。

### ドメインモデルと ID

ドメインモデルは SQLAlchemy を知らない dataclass で、不変条件をメソッドに置きます。
サービスの戻り値はドメインモデルそのものです。
DB から切り離した写しなので、属性を変えても保存されません。保存はサービスだけが行います。
新しく作る集約の ID は UUIDv7 で、`new_id()` で振ります。生成関数はライブラリに 1 つです。
文字列にするのは境界(キー、JSON)だけで、ドメインの型は `UUID` のままです。
個別に指す必要があるものはエンティティとして ID を持ち、そうでなければ値オブジェクトにします。

### トランザクション

ユースケースサービスの 1 メソッドが 1 トランザクションです。
複数の操作を 1 つにまとめるには `transaction()` を使います。
スコープの中のサービス呼び出しと入れ子のスコープは SAVEPOINT を張ります。
例外を握っても、その呼び出しの分だけが戻ります。
async からは `transaction_async()` と `tx.run(fn)` を使います。
Session とサービスは同期のままで、スレッドで呼びます。`AsyncSession` は持ちません。
ContextVar はタスク側で張って戻します。スレッドにはコピーが渡ります。
1 つのスコープを複数のタスクから同時に使うことは禁止です。
新しいスレッドを自分で起こす処理は、ContextVar をコピーして渡さない限りスコープに参加しません。
長い処理(生成、外部 API、オブジェクトの転送)はトランザクションの外で行います。
プールを握ったまま待たないためです。

### 同時更新

ロックの方式は集約ごとに選びます。
読んで直後に書く操作は行ロック(`resolve_by_id_for_update`)です。
読んで、考えて、後から書く操作は版の楽観ロックです。
版を持つ集約は、保存のたびに版を必ず 1 進めます。変更が無くても進めます。
古い版での保存は `ConcurrentUpdateError` になります。
行ロックを取る順序は ID の昇順に固定し、デッドロックを避けます。

### 不変条件の守り方

3 層で守ります。
1 層目はドメインとサービスの検査で、入力の誤りと業務ルールをここで止めます。
2 層目は DB 制約です。直接書き込みを許す以上、最後の砦はここです。
3 層目はフェイクで、DB 制約と同じ検査を DB なしで行います。
DB 制約は `domain/constraints.py` に 1 つずつ宣言します。
制約名、種類(一意、条件付き一意、検査)、キー、違反時の例外です。
本物はこの宣言から制約名と例外の対応表を作り、フェイクはこの宣言で保存時に検査します。
宣言に無い制約の違反は想定外として翻訳しません。
状態を表す列は、サービスの外から更新できません。
ORM の `before_update` が検査し、`GuardedColumnError` にします。
ビューの mapped class は読み取り専用で、flush と ORM の一括文を拒否します。
これらは ORM を通る経路しか止められません。
生 SQL と Core 接続まで止めるには、DB のトリガと GRANT を使います。それが確実な側です。

### 例外

すべての例外は `DomainError(code, message)` の子です。
`code` は `<対象>_<原因>` の小文字で、機械が読みます。`message` は人が読みます。
分類は 3 つだけです。`InputError`、`BusinessRuleError`、`DependencyError` です。
境界(HTTP、キューの入口、ジョブの入口)は分類だけを見て変換します。
想定外の失敗は `DomainError` を継承せず、素のまま境界に届きます。
DB の制約違反は、宣言にあるものだけ翻訳します。
接続の切断、直列化の失敗、デッドロックは `DependencyError` に包みます。
外部依存(オブジェクトストレージ、キュー、外部 API)の失敗も、呼んだ部品が `DependencyError` に包みます。
SQLAlchemy や botocore の例外の型は、呼び出し側に出しません。
冪等にしたい挿入は例外に頼らず、`INSERT ... ON CONFLICT DO NOTHING` で書きます。

### 外部ストレージ

オブジェクトストレージへの配置は、ポート(`ImageStore`)で配ります。
ポートはキーではなくエンティティを受け取ります。
キーの規則はアダプタの内部にあり、ドメインは知りません。
保存の仕方は infra の責務で、リポジトリの行への変換と同じ扱いです。
キーの材料は変わらない ID だけで、拡張子は付けません。
形式やサイズはオブジェクトのメタデータに置き、DB には持ちません。
`content_type` は必須で、put のときに確定させます。
バケットは `ENV` から設定が決めます。ドメインもアプリも知りません。
配置は DB トランザクションの外で行います。
順序は「置いてから行を commit」で、孤児オブジェクトは許容します。
やり直しは、新しい実行として扱うことを基本にします。

### commit 後の知らせ

サービスはドメインイベントを UoW に積みます。
イベントには送り手が ID を振り、受け手がそれで重複を除きます。
発行は一番外側の commit が成功した後に、まとめて順に行います。
SAVEPOINT が戻った分のイベントは捨てます。
発行先は `EventPublisher` ポートで、既定はログです。
Outbox は使いません。commit 後に発行する前にプロセスが落ちると、その知らせは失われます。
送り側は 1 回以下、受け側はブローカーが受け取った後は 1 回以上です。
発行の失敗は呼び出し元に伝えます。書き込みは commit 済みのままです。

### マイグレーション

マイグレーションはライブラリにあり、基盤が所有します。
適用は CI/CD が migrate イメージを別のコンテナで走らせ、アプリのデプロイより先に当てます。
アプリは流さず、待ちません。
ローリング更新中は古いアプリと新しいスキーマが同居します。
マイグレーションは後方互換(expand/contract)で書きます。
`alembic check` を CI の必須にし、モデルとマイグレーションのずれを止めます。

### フェイク

`shop_core.testing` に、UoW、同期と async のスコープ、ストレージ、発行先のフェイクを置きます。
`fake_backend` が全部をまとめて差し替えます。
フェイクは本物と同じ契約です。SAVEPOINT の戻し、制約、版、イベントの規則を同じにします。
フェイクで確かめられないものは、行ロック、生 SQL、状態列の検査、Core 接続です。

## 結果

良い点

- プロセスの種類が増えても、組み立てと検査の形が 1 つです
- 例外の分類が 3 つなので、境界の変換とログがチームをまたいで同じです
- DB 制約の宣言が 1 箇所で、本物とフェイクの振る舞いがずれません
- 保存先の規則がアダプタに閉じ、ドメインとアプリは ID しか知りません
- commit 後の知らせの出し方が 1 つで、アプリが「commit の後に」を手で書きません

受け入れたこと

- ORM の検査(状態列、ビュー)は生 SQL と Core 接続を止めません。確実なのは DB 側です
- Outbox が無いので、commit 直後の障害で知らせが失われます
- 版を必ず進めるので、冪等な再呼び出しでも版が上がります
- フェイクの一意検査は、同時に commit した別の UoW の行を見ません。版の衝突だけは再現します
- async は同期をスレッドで呼ぶので、スレッドプールの大きさが同時実行の上限です
- 資格情報を接続ごとに取るので、取得側で短いキャッシュが要ります
- キーをアダプタが導出するので、規則を変えるときはアダプタが旧規則の面倒を見ます
- 契約の多くは規約で、レビューで守ります
