# ADR 0002: 基盤ライブラリの契約

## ステータス

採用(2026-11-02)。[ADR 0001](0001-shop-core-owned-shared-library.md) を置き換えます。
0001 の決定のうち変えないものも、この文書に再掲します。この文書だけで契約が分かります。

## 用語

- 基盤: 共有ライブラリを所有するチームです。アプリ: それを使う各チームです
- ポート: ライブラリが公開する Protocol です。アダプタ: ポートを実装する infra の部品です
- UoW: Unit of Work です。1 トランザクションの間、リポジトリとイベントを束ねます
- スコープ: `transaction()` が返す、複数の操作を 1 トランザクションにまとめる範囲です
- SAVEPOINT: トランザクションの途中に置く戻り先です。一部だけ戻せます
- 版: 楽観ロックのために集約が持つ整数です。既存の行を保存するたびに進みます
- 状態列: 集約の状態を表す列です。サービスを通さずに変えてはいけません
- フェイク: DB もストレージも使わない、本物と同じ契約の代替実装です
- Outbox: 知らせを DB の表に同じトランザクションで書き、別の仕組みで送る方式です
- lifespan: FastAPI の起動と終了のフックです
- mapped class: SQLAlchemy ORM のテーブルに対応するクラスです
- ContextVar: 実行の文脈ごとに値を持つ変数です。スレッドには自動では渡りません

## コンテキスト

ADR 0001 で、共有パーツを基盤が所有するライブラリとして配ると決めました。
その後、次の事情が加わりました。

- プロセスの種類が増えました(同期の Web、async の Web、async のエージェント、ジョブ)
- 接続情報が 1 本の URL ではなく、環境ごとに別の経路から来ます
- 秘密情報はローテーションされます
- DB のロールが、アプリ用とマイグレーション用に分かれます
- 成果物を DB の外(オブジェクトストレージ)に置きます
- 同じ集約を複数の経路が同時に更新します
- 1 つの親に数十件の追記専用の子が付く集約があります
- チームをまたいで例外の分類を揃える必要があります
- commit の後に外へ知らせを出す必要があります
- DB なしのテストで、一意制約や版の衝突まで再現したい要望があります
- DI ライブラリを依存に入れない方針のプロジェクトがあります
- アプリの使い勝手を、判断の第一の軸にします

## 検討した選択肢

組み立て

- import 時に走る初期化関数: 不採用です。import 順で挙動が変わり、戻り値が無いので差し替えもできません
- 戻り値のある関数を入口で 1 回呼ぶ: 採用です。持ち手が 1 つになり、テストで差し替えられます

DI

- DI ライブラリ(dependency-injector)を使う: 不採用です。ルートごとの `@inject` と `wire` の儀式が増え、Singleton がスレッド安全ではありません
- 素のクラスとデコレータで同じ形を作る: 採用です。遅延 Singleton、Factory、入れ子、差し替えは 60 行で書けます。アプリは FastAPI の `Depends` だけ書きます

資格情報

- 起動時に 1 度読んで固定する: 不採用です。ローテーション後に接続を張り直せません
- 接続を張るたびに取り、認証失敗で 1 回取り直す: 採用です。使わないプロセスは読まず、古い値が残りません

ロール

- アプリとマイグレーションで同じロール: 不採用です。アプリの誤りや侵害でスキーマを壊せます
- アプリ用(DML)と持ち主(DDL)に分ける: 採用です。起動時の検査で取り違えを止められます

ID

- 連番: 不採用です。推測でき、キーの分散も偏ります
- ULID: 不採用です。標準の `UUID` 型に乗りません
- UUIDv7: 採用です。時系列順で、`uuid` 型の列と Python の `UUID` にそのまま乗ります

async

- DB 層を同期と async の 2 本持つ: 不採用です。リポジトリが二重になり、プールも 2 つになります
- DB 層は同期 1 本で、async からはスレッドで呼ぶ: 採用です。ライブラリは 1 本のまま、ループを止めません

複数操作のまとめ方

- 呼び出し側が Session を渡す: 不採用です。サービスの引数が DB の型で汚れます
- ContextVar で暗黙に参加し、SAVEPOINT で区切る: 採用です。サービスの引数を変えずにまとめられます

同時更新

- 行ロックだけ: 不採用です。読んで考えて書く間の衝突を検出できません
- 集約ごとに行ロックと版の楽観ロックを使い分ける: 採用です。操作の形に合わせられます

不変条件

- サービスだけで守る: 不採用です。直接書き込みを許す以上、DB 制約が要ります
- DB 制約を宣言し、本物の翻訳とフェイクの検査を同じ定義から引く: 採用です。本物とフェイクがずれません
- 状態列の保護を ORM だけで行う: 不採用です。生 SQL と Core 接続を止められません
- ORM と DB トリガの両方で守る: 採用です。ORM は早く失敗し、トリガは確実に止めます

冪等な挿入

- 例外を捕まえて既存を返す: 不採用です。制約違反の時点でトランザクションが失敗状態になります
- `INSERT ... ON CONFLICT DO NOTHING`: 採用です。例外が起きません

例外

- 自由に増やす: 不採用です。境界での変換が増え続けます
- code と 3 分類に揃える: 採用です。境界は分類だけを見れば済みます

保存先のキー

- 規則をドメインに置く: 不採用です。保存の仕方は infra の責務で、ドメインに保存の語彙が入ります
- 規則をアダプタに置き、ポートはエンティティを受け取る: 採用です。リポジトリの行への変換と同じ扱いです

配置と commit の順序

- 2 相コミット: 不採用です。オブジェクトストレージは参加できません
- 置いてから行を commit: 採用です。残るのは無害な孤児オブジェクトだけです

commit 後の知らせ

- Outbox: 不採用です。この規模では運用の負担が見合いません
- commit 後に直接送る: 採用です。送り側が 1 回以下になる点を受け入れます

マイグレーション

- アプリの起動時に当てる: 不採用です。複数のアプリが競合し、アプリがスキーマの持ち主になります
- CI/CD が別コンテナで当てる: 採用です。持ち主と順序が 1 つに決まります

公開面の制御

- 技術的に閉じる(別パッケージ化、private 化): 不採用です。使い勝手が落ちます
- `__all__` と、禁止 import を検出するテストで守る: 採用です

## 決定

### 公開面と所有

基盤がライブラリを所有し、uv workspace のメンバーとして配ります。
アプリが import してよいのは 4 つだけです。
`__all__` にある名前、`shop_core.tables`、`shop_core.testing`、`shop_core.fastapi` です。
`infra` と `usecase` の内部は予告なく変えます。
禁止された import は、ライブラリのテストがアプリのソースを走査して検出します。
列は全アプリから見える契約です。列を変えるときは、使うアプリに知らせます。
`code` も公開契約です。変えるときは互換を保ちます。
サービスやテーブルを足す PR は、それを要るチームが書きます。
公開面を変える PR は、呼び出し側の修正も含めます。
基盤は CODEOWNERS で必須レビュアーになり、レビューして取り込みます。
CODEOWNERS と CI の設定はリポジトリの運用で行い、この検証リポジトリには置きません。
「基盤の手を通る」とは、基盤が書くことではなく、基盤がレビューすることです。

### 組み立てと DI

判断の軸は、アプリが触る場所が楽であることです。
触る場所は 4 つです。サービスの受け取り、テストの差し替え、起動、独自の依存の追加です。

import 時には I/O も設定の読み込みも行いません。走るのは定義と ORM のリスナー登録だけです。
組み立ては `build_container(settings)` が行い、`Container` を返します。
戻り値が唯一の持ち手で、モジュール変数には置きません。
呼ぶのはプロセスの入口 1 箇所です。FastAPI の lifespan か `main()` です。
検査は 2 段です。`validate_environment` は I/O なしで設定の形を見ます。
`check_database` と `check_image_store` は接続して確かめ、使うプロセスだけが呼びます。
`check_database` は、ロールとスキーマの版を確かめます。
DB の版がライブラリの期待する版と違えば、起動を止めます。
`build_container` 自体は接続しません。
Engine は `container.engine()` を最初に呼んだときに作られます。

DI ライブラリは使いません。`Container` は素のクラスです。
`provider` デコレータが、各メソッドに 3 つの振る舞いを付けます。
差し替えがあればそれを返し、singleton ならロックして 1 回だけ作り、それ以外は毎回作ります。
singleton は設定、Engine、session_factory、ストア、発行先、各サービスです。
factory は UoW と各スコープです。
サービスは UoW の工場(束縛メソッド)を受け取ります。
サービスが 1 つでも、呼ぶたびに UoW は新しくなります。
アプリの依存は、核の `Container` を属性に持つクラスで入れ子にします。
テストの差し替えは `container.override(名前=工場)` で行い、`fake_backend` はこれを使います。
FastAPI 向けには `shop_core.fastapi` が `Depends` 用の関数を配ります。
アプリは lifespan で `app.state.container` に置き、ルートでは `Depends` だけ書きます。

### 接続と資格情報とロール

接続先は常に `DATABASE_URL` で渡します。
項目別の環境変数で受けるときは、アプリの入口で `Settings` を組み立てて渡します。
URL に埋めるパスワードは URL エンコードします。
Engine の作り方は `build_container(engine_factory=...)` で外から差し込めます。
渡さなければ `Settings.from_env()` から作ります。
資格情報がローテーションされる環境では、`build_container(credentials=fn)` を使います。
このとき URL のユーザー名とパスワードは無視します。
新しい接続を張るたびに `fn` を呼びます。
認証失敗のときだけ `fn` を呼び直し、1 回だけやり直します。
`fn` は複数のスレッドから同時に呼ばれます。
`fn` の失敗は `DependencyError` になります。
起動時に読んで固定しません。
ローテーションは、同じロール名でパスワードだけを替えます。
接続ごとに `statement_timeout` と `lock_timeout` を設定できます。既定は無制限です。
`search_path` は接続の起動パラメータで設定します。プロキシを挟むときは通ることを確かめます。
DB のロールは 2 つです。
アプリ用は、スキーマの USAGE、テーブルの DML、シーケンスの USAGE と SELECT だけです。
ビューは SELECT だけです。
持ち主(マイグレーション用)は DDL を持ちます。
ロールの作成は DB の初期化で行い、GRANT はマイグレーションで行います。
新しいテーブルの GRANT は、既定権限(ALTER DEFAULT PRIVILEGES)で自動的に付きます。
新しいビューは、作るマイグレーションで DML を REVOKE します。
既定権限は、持ち主ロールでマイグレーションを流したときだけ効きます。
アプリ用ロールが無い DB(テスト用)では、GRANT のマイグレーションは何もしません。
起動時に `check_database` が `assert_app_role` を呼びます。
接続中のロールがスキーマに CREATE できれば、起動を止めます。
スキーマ名は `infra/schema.py` の定数 1 つで、`public` は使いません。
`ENV` の値は `local`、`stg`、`prd` の 3 つだけです。
環境変数の名前と既定値は基盤の規約で、一覧は README に置きます。

### ドメインモデルと ID

ドメインモデルは SQLAlchemy を知らない dataclass で、不変条件をメソッドに置きます。
サービスの戻り値はドメインモデルそのものです。
DB から切り離した写しなので、属性を変えても保存されません。保存はサービスだけが行います。
今後足す集約の ID は UUIDv7 で、`new_id()` で振ります。生成関数はライブラリに 1 つです。
文字列にするのは境界(キー、JSON)だけで、ドメインの型は `UUID` のままです。
個別に指す必要があるものはエンティティとして ID を持ちます。
そうでないものは値オブジェクトにします。

追記専用の子(1 つの親に数十件付く記録)は、集約に読み込みません。
追記は別のリポジトリのメソッドで行います。
親ごとの連番は、親の行の `UPDATE ... RETURNING` で振ります。
この UPDATE は親の行ロックを取り、同じ親への追記を直列にします。
連番の UPDATE は親の版を進めません。
連番はポートのメソッドで振り、フェイクも同じ規則で振ります。

### トランザクション

ユースケースサービスの 1 メソッドが 1 トランザクションです。
複数の操作を 1 つにまとめるには `transaction()` を使います。
スコープの中では、サービス呼び出しと入れ子のスコープごとに SAVEPOINT を張ります。
例外を握っても、その呼び出しの分だけが戻ります。
直接 SQL には SAVEPOINT が張られません。
直接 SQL の失敗はスコープ全体を中断します。囲みたいときは入れ子の `transaction()` を使います。
1 トランザクションで SAVEPOINT を張る回数は 50 回までにします。
数十件の追記は、ループでサービスを呼ばず、1 回のサービス呼び出しで行います。
async からは `transaction_async()` と `tx.run(fn)` を使います。
Session とサービスは同期のままで、スレッドで呼びます。`AsyncSession` は持ちません。
ストレージと発行先も、async からは `run_sync` で呼びます。
ContextVar はタスク側で張って戻します。スレッドにはコピーが渡ります。
1 つのスコープを複数のタスクから同時に使うことは禁止です。
スコープの中で起こしたタスクは、スコープより長く生きてはいけません。
エージェントのループ全体はスコープで囲みません。スコープはツール呼び出しごとに張ります。
自分で起こしたスレッドや executor は、ContextVar をコピーして渡さない限り参加しません。
参加しない処理は別のトランザクションとして動き、外側のロックと待ち合います。
長い処理(モデルの推論、外部 API、オブジェクトの転送)はトランザクションの外で行います。
プールを握ったまま待たないためです。
同時実行の上限は、接続プールとスレッド上限の小さい方です。
async のプロセスは、スレッドの上限をプールの接続数に合わせます。

### 同時更新

ロックの方式は集約ごとに選びます。
読んで直後に書く操作は行ロック(`resolve_by_id_for_update`)です。
読んで、考えて、後から書く操作は版の楽観ロックです。
この操作は、読んだときの版をサービスに渡します。
版が合わなければ、サービスは何も変えずに `ConcurrentUpdateError` を投げます。
版を持つ集約は、既存の行を保存するたびに版を 1 進めます。変更が無くても進めます。
ただし、冪等な再呼び出しで何も変わらないときは保存せず、版も進めません。
新規の行は版 0 で入れます。
版を持つ集約は `shop_core.tables` から更新しません。版の管理はリポジトリだけです。
状態遷移の前提(実行中のときだけ完了にする、など)はサービスが守ります。
そのため、版を渡すのは、読んだ中身を前提に何かを作って保存する操作だけです。
ライブラリは `ConcurrentUpdateError` を再試行しません。
呼び出し側が読み直し、操作全体をやり直します。
やり直しは回数を限り、超えたら失敗として記録します。
高い処理の結果は捨てず、前提が変わっていなければ保存だけをやり直します。
複数の行をロックするときは、集約の種類、次に ID の昇順で取ります。
`transaction()` の中で自分でロックを取る処理も、同じ順序を守ります。

### 不変条件

3 層で守ります。
1 層目はドメインとサービスの検査で、入力の誤りと業務ルールをここで止めます。
2 層目は DB 制約とトリガです。直接書き込みを許す以上、最後の砦はここです。
3 層目はフェイクで、DB 制約と同じ検査を DB なしで行います。
DB 制約は `domain/constraints.py` に 1 つずつ宣言します。
宣言する項目は、制約名、種類(一意、条件付き一意、検査)、キー、違反時の例外です。
本物の実装は、この宣言から制約名と例外の対応表を作ります。
フェイクは、同じ宣言で保存時と commit 時に検査します。
新しい制約は、宣言、マイグレーション、フェイクの集約の表の 3 箇所に書きます。
宣言に無い制約の違反は想定外として翻訳しません。
宣言した制約名が DB に存在することは、カタログと突き合わせるテストで固定します。
条件付き一意に対する冪等な挿入は、`ON CONFLICT` に同じ述語を付けます。
状態列は、サービスの外から更新できません。
ORM の `before_update` で検査し、違反は `GuardedColumnError` にします。
DB 側でも守ります。UoW がトランザクション内に `app.in_service` の設定を立てます。
BEFORE UPDATE トリガがその設定を見て、無ければ更新を拒否します。
トリガの拒否も、ライブラリは `GuardedColumnError` に翻訳します。
ORM の検査は早く失敗するためのもので、確実に止めるのはトリガです。
insert の初期値は検査の対象外です。
ビューの mapped class は読み取り専用です。flush と ORM の一括文は拒否します。
アプリ用ロールはビューに SELECT しか持たないので、生 SQL でも書けません。
ビューは読み取り側(画面用の view model)のための任意の手段です。生 SQL も許可します。

### 例外

ドメインの失敗を表す例外は、すべて `DomainError(code, message)` の子です。
`DomainError` は、全社共通の基底例外があればその子にします。
呼び出し側のプログラムの誤り(`GuardedColumnError`、`SettingsError`、引数の不正)は `DomainError` にしません。
`code` は `<対象>_<原因>` の小文字で、機械が読みます。`message` は人が読みます。
分類は 3 つです。`InputError`、`BusinessRuleError`、`DependencyError` です。
`InputError` は権限の誤りも含みます。権限の誤りは `code` で見分けます。
`InputError` の下位に `NotFoundError` があり、境界は 404 への変換にだけこれを使います。
境界(HTTP、キューの入口、ジョブの入口)は、分類と `NotFoundError` だけを見て変換します。
想定外の失敗は `DomainError` を継承せず、素のまま境界に届きます。
DB の制約違反は、宣言にあるものだけ翻訳します。
接続を張れない失敗、接続の切断、プールの枯渇、文とロックの時間切れは `DependencyError` です。
直列化の失敗とデッドロックも `DependencyError` です。
外部依存の失敗も、呼んだ部品が `DependencyError` に包みます。
対象はオブジェクトストレージ、キュー、外部 API です。
`DependencyError` の `retryable` が偽なら、再試行しません。
`DependencyError` を再試行してよいのは、その書き込みが冪等なときだけです。
commit の最中に接続が切れたときは、commit が通ったかどうか分かりません。
宣言にある制約違反と、分類した DB 障害では、SQLAlchemy の例外の型を出しません。
それ以外の DB 例外は想定外なので、そのまま届きます。
冪等にしたい挿入は例外に頼らず、`INSERT ... ON CONFLICT DO NOTHING` で書きます。

### 外部ストレージ

オブジェクトストレージへの出し入れは、ストレージ用のポートを通します。
ポートはキーではなくエンティティを受け取ります。
キーの規則はアダプタの内部にあり、ドメインは知りません。
保存の仕方は infra の責務で、リポジトリの行への変換と同じ扱いです。
キーの材料は変わらない ID だけで、拡張子は付けません。
形式やサイズはオブジェクトのメタデータに置きます。真実はストレージ側です。
一覧や絞り込みに使う属性は、DB にも写しを持ちます。
ユーザーメタデータは合計 2 KB までで、ASCII だけです。
`content_type` は必須です。空と `binary/octet-stream` は `ValueError` で拒否します。
バケット名は設定が決めます。既定は `ENV` から導き、環境変数で上書きできます。
ドメインもアプリもバケット名を知りません。
署名付き URL は公開用のエンドポイントで作ります。内部用と分けられます。
署名付き URL の有効期間は、認証情報の期限を超えません。
配置は DB トランザクションの外で行います。
順序は「置いてから行を commit」で、孤児オブジェクトは許容します。
孤児オブジェクトは、定期の棚卸しで消します。
失敗した処理は直さず、新しい試行として別の集約にします。

### commit 後の知らせ

サービスはドメインイベントを UoW に積みます。
イベントには送り手が ID を振り、受け手がそれで重複を除きます。
ブローカーのメッセージ ID には、この ID を使います。
発行は一番外側の commit が成功した後に、まとめて順に行います。
SAVEPOINT が戻った分のイベントは捨てます。
冪等な再呼び出しはイベントを出しません。
発行先はポート(`EventPublisher`)で、差し替えは `build_container(publisher=...)` で行います。
`local` 以外の環境では、発行先の指定を必須にします。既定のログは `local` だけです。
発行先はスレッド安全に書き、短い時間で戻します。
発行の失敗は `EventPublishError` で伝えます。この例外は書き込みが済んだことを示します。
境界はこれを再試行可とは扱わず、書き込みをやり直しません。
複数のイベントの途中で失敗すると、残りは失われます。
Outbox は使いません。commit の後、発行の前にプロセスが落ちると、その知らせは失われます。
送り側の保証は 1 回以下です。ブローカーが受け取った後は、受け側の保証が 1 回以上になります。

### DB への直接アクセス

行ロック、LISTEN/NOTIFY、autocommit のために、`container.db()` が接続の窓口を返します。
Engine や sessionmaker は出しません。窓口を 1 つに絞ります。
この窓口にフェイクはなく、`fake_backend` でも差し替わりません。
`listen()` は接続を 1 本占有します。リスナーの数だけプールが減ります。

### マイグレーション

マイグレーションはライブラリにあり、基盤が所有します。
適用は CI/CD が migrate イメージを別のコンテナ(Job)で走らせます。
アプリの展開より先に、1 回だけ流します。
Job が失敗したら、アプリの展開を進めません。
migrate の同時実行は advisory lock で直列にし、DDL には `lock_timeout` を付けます。
migrate は持ち主ロールで、`DATABASE_URL` だけを読みます。`credentials` は使いません。
アプリはマイグレーションを流さず、完了も待ちません。
アプリは起動時にスキーマの版を確かめ、古ければ起動を止めます。
古いアプリと新しいスキーマの同居は、ローリング更新中に限らず、チームごとの展開でも起きます。
マイグレーションは後方互換(expand/contract)で書きます。
contract は、旧版のアプリが消えた次のリリースで行います。
本番では downgrade を使わず、新しい版で直します。
CI では `alembic check` を必須にし、モデルとマイグレーションのずれを止めます。

### 依存とビルド

イメージはアプリごとに、ワークスペースのルートから `uv sync --frozen --package` で作ります。
lock はワークスペースに 1 つで、基盤が更新します。
基盤の依存は、全アプリのイメージに入ります。
依存は、公開から 7 日たった版だけを入れます。`exclude-newer` の日付は手で進めます。
arm64 のイメージは CI で実際にビルドして確かめます。
UUIDv7 は標準ライブラリに入るまで追加パッケージを使います。

### フェイク

`shop_core.testing` に、UoW、同期と async のスコープ、ストレージ、発行先のフェイクを置きます。
`fake_backend` が全部をまとめて差し替えます。
フェイクは本物と同じ契約です。SAVEPOINT の戻し、制約、版、イベントの規則を同じにします。
フェイクの commit は、その UoW で変えた分だけを共有状態に書きます。
先に commit した別の UoW の書き込みは消えません。
一意制約は commit 時にも共有状態に対して検査し、同時 commit の衝突も再現します。
フェイクの `tx` は `session` を持ちません。それを使う処理は切り出して差し替えます。
フェイクで確かめられないものは、行ロック、生 SQL、状態列のトリガ、Core 接続、連番の衝突です。

### 守る主体

| 規則 | 守る主体 |
|---|---|
| import してよい名前 | コード(テストがアプリのソースを走査) |
| 組み立てを入口で 1 回だけ呼ぶ | レビュー |
| アプリ用ロールで起動する | コード(`check_database`) |
| スキーマの版が合う | コード(`check_database`) |
| `local` 以外で発行先を指定する | コード(`build_container`) |
| 1 つのスコープを並行に使わない | レビュー |
| 自分で起こしたスレッドでスコープに参加する | コード(呼び出し側が ContextVar をコピー) |
| 長い処理をトランザクションの外に出す | レビュー |
| SAVEPOINT の回数 | レビュー |
| ロックの取得順 | サービスはコード、直接のロックはレビュー |

## 結果

### 利点

- プロセスの種類が増えても、組み立てと検査の形が 1 つです
- アプリは `Depends` と `fake_backend` と入口の 3 行だけを書きます
- DI ライブラリへの依存が無く、Singleton のスレッド安全も自前で保証します
- 例外の分類が 3 つなので、境界の変換とログがチームをまたいで同じです
- DB 制約の宣言が 1 箇所で、本物とフェイクの振る舞いがずれません
- 状態列はトリガで守るので、生 SQL でも破れません
- 保存先の規則がアダプタに閉じ、ドメインとアプリは ID しか知りません
- commit 後の知らせの出し方が 1 つで、アプリが「commit の後に」を手で書きません
- 古いスキーマのアプリは起動時に止まり、最初のクエリで壊れません

### 受け入れる制約

- Outbox が無いので、commit 直後の障害で知らせが失われます
- 発行は応答時間に乗ります。発行が失敗すると、書き込み済みのままエラーが返ります
- 既存の行を保存するたびに版が進むので、何も変えない保存も他の書き手を失敗させます
- 同じ操作を同時に 2 回行うと、片方は `ConcurrentUpdateError` になります
- サービス呼び出しごとに SAVEPOINT と設定の往復が増えます
- 認証失敗の取り直しで、接続ごとに最大 2 回の資格情報取得が起きます
- 既存の接続は古い資格情報のまま生き、切れたときに新しい資格情報で張り直します
- 資格情報の取得が遅いと、プールの貸し出しが止まります。キャッシュの期間はローテーションの猶予より短くします
- async は同期をスレッドで呼ぶので、プールとスレッド上限の小さい方が同時実行の上限です
- 自分で起こしたスレッドは、黙って別のトランザクションになります
- 制約は宣言、マイグレーション、フェイクの表の 3 箇所に書きます。宣言の漏れはテストで検出できません
- アプリ用ロールが無い DB では、GRANT のマイグレーションは何もしません
- 既定権限は、持ち主ロールでマイグレーションを流したときだけ効きます
- 署名付き URL は公開用エンドポイントの設定に依存します
- ローカルの S3 互換モックは、CopyObject で Content-Type を置き換えず、認証情報を検査しません
- ストレージの put は全量をメモリに載せます
- UUIDv7 は標準ライブラリに入るまで追加パッケージが要ります
- キーをアダプタが導出するので、規則を変えるときはアダプタが旧規則の面倒を見ます
- 契約の多くはレビューで守ります。守る主体の表を参照してください
