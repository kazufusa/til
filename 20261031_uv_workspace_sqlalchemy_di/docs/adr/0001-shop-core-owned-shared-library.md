# ADR 0001: 共有パーツを基盤が所有するライブラリ shop_core として配る

## ステータス

置換(2026-11-01)。[ADR 0002](0002-shared-library-contract.md) に置き換えられました。
採用は 2026-10-31 で、配備前の 2026-11-01 に一部を改訂し、同日に 0002 で置き換えました。
以下は置き換え時点の内容を、記録として残したものです。

## コンテキスト

複数のアプリと基盤チームが、同じ DB を使います。
基盤チームは、テーブルの扱いと DB の作法を、全アプリに守らせたいと考えています。
心配なのは、ORM に触れること自体ではありません。
不変条件とトランザクション境界が、アプリごとに散らばることです。
Session の寿命や lazy load の扱いも、チームごとにばらつきます。

一方で、アプリのコードに DB の知識を持ち込ませず、DB なしで速くテストできる必要があります。
配布は、1 つのリポジトリの中で完結する形が望ましい状況です。

## 検討した選択肢

- サービスとドメインを workspace のパッケージにし、公開面を狭くする: 採用
- サービスを介さず ORM だけを共有し、不変条件もアプリに任せる: 不変条件がアプリに散るため不採用。mapped class の配布自体は、サービスと DB 制約を併用する形で採用
- アプリごとに DB アクセスを持つ: 作法が割れ、スキーマの所有者も曖昧になるため不採用
- 読み取り専用の mapped class とアプリ別スキーマに分ける: 試して不採用。基盤がアプリの事情を抱え、二重の線引きで使い勝手が落ちたため
- HTTP API を持つ別サービスにする: 運用と遅延の負担が、この規模に見合わないため不採用

## 決定

### 公開面

`packages/shop_core` を uv workspace のメンバーにし、アプリは `shop-core = { workspace = true }` で依存します。
アプリが import してよいのは、`__all__` にある名前、`shop_core.tables`、`shop_core.testing` だけです。
`infra` と `usecase/uow.py` は内部構造なので、import を禁止し、予告なく変更します。

### ドメインモデル、ORM、リポジトリ

ドメインモデルは、SQLAlchemy を import しない dataclass で、不変条件をメソッドに置きます。
ORM の Row は `infra` に置き、アプリには `shop_core.tables` の別名で見せます。
モデルとの変換と、それに必要な読み込みは、`infra/repositories.py` だけが行います。
リポジトリは `domain/ports.py` の Protocol で、メソッド名は `store` と `resolve_by_*` にそろえます。
行ロックは `resolve_by_id_for_update` を Protocol に置き、フェイクでは `resolve_by_id` と同じです。

### トランザクション境界と ambient transaction

ユースケースサービスは UoW の factory を受け取り、1 メソッドを UoW のスコープの中で完結させます。
書き込みは commit で確定し、UoW は終了時に必ず Session を閉じ、例外のときは rollback します。
アプリは `Session` の生成も `commit()` も書きません。
複数の操作を 1 トランザクションにするには、`container.transaction()` を使います。
`usecase/transaction.py` が Session を ContextVar に置き、スコープ内の UoW はその Session に参加します。
参加した UoW はセーブポイントを張り、commit で解放し、例外なら戻します。
close は外側が行います。入れ子のスコープも同じです。

### DI

DI には dependency-injector を使い、`Container` を基盤が持ちます。
設定、engine、session_factory、db は Singleton、UoW と transaction は Factory です。
サービスは Singleton で、UoW の provider を受け取り、呼ぶたびに UoW を作ります。
アプリは独自の依存を `providers.Container` で入れ子にします。

### 接続設定

`Settings.from_env()` は、`DATABASE_URL` を必須、`SQL_ECHO` と `DB_POOL_*` を任意で読みます。
必須の変数がないか、数値でない値があれば、`SettingsError` を投げます。
設定は engine を最初に作るときに読むので、フェイクのテストに環境変数は要りません。
環境変数の名前と未設定時のエラーは基盤の規約で、アプリごとには決めません。

### フェイクの同梱

`testing.py` に、フェイクの UoW と transaction、それをまとめて差し替える `fake_backend` を置きます。
フェイクは本物と同じ契約を守ります。
ただし transaction のフェイクは `tx.session` を持たないので、それを呼ぶコードは切り出して monkeypatch します。

### DB への直接アクセス

行ロックや LISTEN/NOTIFY のために、`container.db` が接続、autocommit、listen、notify の窓口を返します。
engine や sessionmaker を出すと、アプリが接続の作り方まで握ってしまうので、窓口を 1 つに絞ります。
この窓口にフェイクはなく、`fake_backend` でも差し替わりません。

### ORM の公開

アプリは、画面の都合で決めた view model を読み取り用に自由に組んで構いません(読み取りと書き込みを分ける CQRS の読み取り側)。
基盤は、すべてのテーブルの mapped class を `shop_core.tables` で配ります。書き込みもできます。
スキーマは `shop` の 1 つで、すべて基盤が管理します。
接続の search_path も `shop` にするので、生 SQL でスキーマ名を省けます。
不変条件が絡む操作(在庫の引き当て、注文の作成)は、サービスを使います。
サービスが無い単純な insert や update は、ORM で直接書いて構いません。
入力の検査(数量、価格、在庫の符号)はドメインとサービスが行い、`stock >= 0` や `quantity > 0` の DB 制約は最後の砦です。
生 SQL も許可します。
SQL ビューは集計のための任意の手段です。
ビューの mapped class だけは読み取り専用にし、flush と ORM の一括文による書き込みを `RuntimeError` で拒否します。
単純なビューは Postgres が書き込みを通すためです。
Core の接続からの書き込みは止まらないので、確実な防御は、ビューに SELECT だけを持つ DB ロールです。

### マイグレーションの所有

マイグレーションは `packages/shop_core/migrations` に置きます。
適用は CI/CD パイプラインが行い、アプリの起動の連鎖には含めません。
パイプラインは migrate イメージを別の Docker コンテナとして走らせ、アプリのデプロイより先に `alembic upgrade head` を当てます。
パイプラインの実装はこのリポジトリの範囲外で、役割だけを決めます。
アプリは alembic を実行せず、完了も待ちません。
テーブルや列が欲しいときは、アプリが基盤に依頼します。

## 結果

良い点

- サービスを使う操作では、アプリのコードに Session も SQL も現れず、DB の作法を基盤が一括で変えられます
- アプリのテストが DB なしで動き、ロールバックの挙動も確かめられます
- テーブルの所有者が 1 つで、スキーマの変更履歴も 1 本の系列に残ります

受け入れたこと

- import 禁止は規約で、レビューで守ります
- サービスを使うかどうかはアプリの判断です。DB 制約で表せない不変条件は、規約でしか守れません
- ContextVar を使うので、新しいスレッドのコードは呼び出し元のスコープに参加しません。asyncio のタスクは同じ Session を共有するため、スコープ内で並行に使えません
- フェイクで確かめられないものがあります。行ロックと直接 SQL です
- テーブルの追加や変更は基盤チームの手を通ります。アプリの開発速度より、スキーマの一元管理を優先しました
- 列は全アプリから見える契約になるので、列の変更はアプリへの通知が要ります
- view model の形はアプリごとに増えます。共通化は、必要になったときに決めます
- `listen()` は接続を 1 本占有します。リスナーの数だけプールが減ります
- デプロイの順序(マイグレーションが先、アプリの展開が後)はパイプラインの責任です。古いスキーマで起動したアプリは最初のクエリで失敗し、アプリはスキーマの版を確認しません
